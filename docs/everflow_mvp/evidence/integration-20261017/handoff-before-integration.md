## 1. 열어야 할 씬과 실행 순서

Unity 시작의 Safe Mode `CS0103`은 새 helper가 실제 컴파일 목록에 빠져 발생했다. Refresh만으로 해결되지 않아 helper를 이미 인식되는 `EFCanalExperimentTests.cs` 안에 합쳤으며, 이후 실제 Play 보고서 생성으로 컴파일 차단 해소를 확인했다. 원래 helper 파일과 meta는 안내 주석 상태로 보존했다. 과거 오류 증거는 `evidence/resume-20261017/editor-cs0103-20261017T042616Z.json`이다.

1. 정상 Windows 사용자 `vzd12`의 Unity Hub에서 이 프로젝트를 Unity 6000.3.21f1로 연다. 이미 열려 있으면 그 창을 사용한다. 라이선스 파일 변경은 필요하다고 판단하지 않았다.
2. **이미 존재하는** `Assets/Scenes/Everflow_Map_P3_DesignTest_20261016.unity`를 연다. `Create P3 Copy`를 다시 실행하지 않는다. 기존 사본을 덮어쓰지 않는다.
3. Play 중이면 중지하고 스크립트 컴파일 완료 후 `Tools > EVERFLOW > MVP Experiment > Run P3 Checks`를 실행한다. 이 메뉴가 자체적으로 Play에 진입한다.
4. 새 `docs/everflow_mvp/evidence/p3-checks-*.txt`를 확인한다. 먼저 출발대 진단과 동일 높이 중첩/높은 다른 바닥 거부 검사를 본다. API fixture·잎 이동 구간·전체 횡단은 구분한다.

접근 수리는 이미 실행했다. `p3-access-repair-20261017T043626193Z-16390a32.json`과 같은 시각의 byte 백업을 보존했다. 사본에서49개 생성 계단 Transform만 변경했고 나머지 씬 블록/보호 자산은 동일하다. `Repair P3 Access`를 이유 없이 다시 실행하지 않는다. 다음은 수정된 검사로 Run P3 Checks 재실행이다.

반복 검사용 연결: 정상 Editor에서 `Enable Local Check Bridge`를 한 번 누르면 같은 세션 동안 아래 CLI가 **수로 검사/접근 수리 두 명령만** 전달한다. 기본 비활성, Editor 재시작 시 해제, Disable 메뉴로 중단 가능하다. 임의 메서드/셸/원본 씬 저장은 허용하지 않는다. Play·컴파일·임포트·unsaved scene·중복 실행은 거부하고 수락과 실제 결과를 구분한다. CLI는 실제 로드된 연결 revision2도 확인한다. 소스 stamp는 변경 감지 수단이며 DLL 컴파일 증명으로 취급하지 않는다.

```powershell
python -B tools/request_mvp_editor.py status
python -B tools/request_mvp_editor.py p3-checks
```

검사 요청 후 최종 보고서를 확인한다. CLI 자체가 Unity를 새로 실행하거나 기존 Editor를 종료하지 않는다.

원본 확인은 `Assets/Scenes/Everflow_Map.unity`. 기존 Title의 게임 시작 버튼은 계속 원본 Map을 연다. 실험 씬이 release build 목록에 등록되었다고 가정하지 않는다. 실험 작업 중 기존 `Apply Integration`/`Apply Presentation` 메뉴는 실행하지 않는다.

CLI의 계정/중복 실행 가드와 진단은 다음과 같다. 이 코딩 터미널에서 배치 Editor 실행은 계정 차이 때문에 차단된다. 아래 `test`는 Editor가 모두 닫힌 정상 사용자 터미널에서만 대안으로 사용한다.

```powershell

python tools/run_mvp_experiment_unity.py diagnose
python tools/run_mvp_experiment_unity.py test
```

이미 Editor가 실행 중이면 배치 도구가 거부하므로 해당 Editor의 메뉴를 사용한다. 생성 실패로 남은 사본은 먼저 검토·보관하고 수동 판단한다. 도구가 원본이나 부분 사본을 자동 삭제하지 않는다.

이 환경에서 Unity 창을 직접 조작하는 앱 연결은 없고, 공식 CLI는 Pipeline 미설치·서버 접속 불가, 기존 MCP 연결 정보도 없다. `unity status`의 빈 결과만으로 Editor 종료나 라이선스 만료를 단정하지 않았다. 최신 계정·CLI 진단과 민감정보를 제외한 로그 발췌는 `evidence/followup-20261016/environment-diagnosis-20261017T041118165091Z.json`에 있다. 배치 실패 명령 반복, 기존 Editor 강제 종료, 보호 설정 변경은 하지 않았다.

## 2. 실제 바뀐 플레이

아래 배치는 저장된 실험 씬에 실제 존재한다. 수로 전체 이동·카메라 시야는 아직 검증되지 않았다.

펌프를 낮은 정비 마당으로 옮기고 물 집수조·공급관을 높은 수로와 연결했다. 낮은 집수조 또는 높은 출발대에서 같은 물을 얼릴 수 있다. 짧은 측면 계단을 올라 기존 잎 이동으로 수로를 내려와 도약하고, 마당보다 높은 넓은 데크에 착지한 뒤 완료 선까지 직접 걷는다. 출발대 실제 접지 후 CP를 저장하며 추락 시 준비 상태를 유지한다. 보조 완료 후 물·얼음·공급 상태를 안정화한다.

기본 이동·점프·카메라·입력 수치는 보존했다. 원본 타이틀/HUD/모델/공용 프리팹/빌드 설정 파일은 해시로 보존 확인했다.

## 4. 직접 검증과 미검증

실제 수행: 문서/코드/씬 직렬화 읽기 조사, 실제 에이전트 3명 역할 분담과 독립 검토, 설치 Unity DLL 기반 C# 세 정의 컴파일, GUID/meta 검사, 322개 기준 파일 SHA256 비교, Python 문법·diff 검사. 상세·증거는 `VERIFICATION.md`와 `evidence`를 본다.

최초 샌드박스 배치 실행은 IPC 오류로 실패했다. 이후 정상 사용자 Hub 실행 로그(2026-10-16 22:28 KST)는 라이선스 연결·갱신 성공과 2027-07-14 만료일을 기록했다. 실제 실험 씬이 생성되었고 `p3-checks-20261016-132900-485.txt`에 2개 Editor 항목 PASS, runtime/API fixture 17개 PASS, 출발대 지지 FAIL이 기록되어 있다. 소스 컴파일 성공과 이 부분 Play 실행을 전체 완주·빌드 성공으로 계산하지 않는다.

사람의 초심자 이해도·재미·목표 플레이시간은 미검증이다.

## 5. 남은 결함과 위험

- **기존 P6는 마지막 별도 입력 없이 준비 조건 충족으로 엔딩을 시작한다.** 이번 P3 회차에서는 미수정이다. 최종 제어부 도달 자동 완료는 없지만, 요청한 최종 직접 PULSE/실제 횡단 조건은 충족하지 않는다.
- 수리 후 첫 계단→마당과 낮은 타깃 실제 조준/능력 입력은 검증했다. 측면 계단 이후 연속 경로와 높은 타깃은 미검증이다. 컴파일 성공으로 이동 성공을 보장하지 않는다.
- 출발대 동높이 중첩 문제는 새 Play에서 수정 효과와 첫 hit 순서가 확인되었다. 다음 실패는 종점에서 고정 갑판보다7cm 높은 잎을 밟고 있어 발생한 테스트 가정 문제다. 실제 걸어 내려온 뒤 고정 데크를 확인하도록 수정했으며 재실행이 필요하다.
- 실험 생성 중 오류가 나면 부분 사본/미저장 변경이 남을 수 있다. 실패 기록을 확인하고 그 사본을 완료본으로 사용하지 않는다.
- 타이틀은 실험 사본 진입 경로가 아니다. 전체 검토/빌드 경로는 P3 통과 후 별도 안전 통합이 필요하다.
- P5 역할과 실제 번호가 다르다. 회전 연결기는 UI P3, 요청 수로는 UI P4이며 실제 UI P5는 뿌리·문이다.

## 6. 원복 방법

원본 씬을 직접 열면 기존 배치로 돌아간다. 현재 실험 사본은 실제 존재하므로 보관한다. 이번 재개의 지지 판정 수정만 원복하려면 `EFCanalExperiment.IsStandingOn`의 변경 부분을 검토한다. 기존 기능 전체를 무단 checkout/reset하거나 사용자 `improvement_plan.md`를 삭제하지 않는다. 공유 자산/빌드 목록은 이번 재개에서 변경하지 않았다.

## 7. 먼저 확인할 5가지

1. 새 Run P3 Checks 보고서에서 출발대 지지 실패가 해소되었고 거부해야 할 공중/다른 높은 바닥을 계속 거부하는가.
2. 낮은 마당에서 펌프·집수조·높은 출구 관계가 보이고 두 위치에서 FREEZE가 가능한가.
3. 새 계단과 실제 잎 경로가 충돌 없이 높은 출구에 도착하는가.
4. 출발대/수로/끝단 추락 후 준비 유지, 출발대 CP와 완료선의 공중 통과 거부, 안전 가장자리 보조 인정이 맞는가.
5. R과 Restart의 차이·반복 재시작·HUD/카메라 유지, 기존 P6 자동 준비 엔딩 결함이 다음 통합에서 해결되는가.
