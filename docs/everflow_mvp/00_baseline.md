# EVERFLOW MVP 개선 전 구조 조사

작성일: 2026-10-16. 담당: 구조 조사 하위 에이전트. 이 문서는 개선 구현 전 읽기 전용 조사 기록이다. 아래 코드 경로와 줄 번호는 조사 시점 기준이며, 이후 수정으로 달라질 수 있다.

## 1. 조사 범위와 증거의 한계

- `improvement_plan.md`를 확인했다. 이 문서의 사용자 보고와 제안 배치는 현재 Unity 씬에서 실행 검증된 사실과 구분한다.
- 프로젝트 아래 `AGENTS.md`를 재귀 검색했으며 발견하지 못했다. 기존 코드, Editor 도구, `docs/map-integration`, `docs/ability-validation`, `docs/ui-progress`의 구조를 참고했다.
- 조사 시작 시 `git status --short` 결과는 `?? docs/everflow_mvp/`였다. 이 폴더의 사용자 제공 기획 문서를 보존하며, 조사 담당은 이 기준 문서 외의 파일을 수정하지 않는다.
- `Assets/EverflowMap/Runtime`, 관련 Editor 도구, 실제 `Assets/Scenes/Everflow_Map.unity` 직렬화 항목, 타이틀 코드, 프로젝트 설정을 읽었다. 씬 YAML은 읽기만 했고 수동 편집하지 않았다.
- 이 문서의 실행 동작 설명은 **코드·직렬화로 확인한 구조**다. 이번 조사 담당은 Unity 실행, Editor 플레이, 빌드 생성, 실제 빌드 실행을 수행하지 않았다. 이전 저장소 검증 결과나 테스트 코드는 이번 회차 실행 증거가 아니다.
- 총괄이 Unity 실행을 1회 시도했고 licensing IPC refused 로그 부근에서 진행하지 못했다는 사실을 전달받았다. 실행 가능 여부의 추가 조사가 진행 중이므로, 이 사실만으로 영구적인 실행 불가를 확정하지 않는다.
- 이 조사 시점에는 새 실험 통합 씬과 새 빌드를 생성하지 않았다. 이후 생성·검증 결과는 `WORKLOG.md`, `VERIFICATION.md`, `HANDOFF.md`가 최종 기록이다.
- 개발자 원본 플레이시간, 초심자 이해도·재미, 목표 플레이시간 달성률, 성능은 측정하지 않았다. 관련 추정치를 사실로 제시하지 않는다.

## 2. 자료와 실제 진행 ID의 차이

실제 런타임은 `EFMapWorld.stages[0..5]`로 6단계를 관리한다. 사용자 보고의 6요소와 현재 UI의 P 번호는 일치하지 않는다. `EFMapSetup.cs:84–150`의 구성과 실제 씬 `Everflow_Map.unity:5377–5467`의 stage 직렬화를 함께 확인했다.

| 사용자 설명의 역할 | 현재 실제 구현과 진행 ID | 근거와 처리 주의 |
|---|---|---|
| P1 꽃 점프대 | index 0/UI P1의 첫 부분 | 같은 stage에 덩굴도 포함한다. |
| P2 덩굴 이동 | index 0/UI P1의 두 번째 부분 | 별도 stage가 아니다. 실제 UI P2는 낙하 파편 3개와 슬레이트다. |
| P3 펌프→물→결빙→슬라이드·도약 | index 3/UI P4 | 실제 source4→gate4→water→leaf 경로다. 실제 UI P3는 회전 다리다. |
| P4 잎 슬라이딩 | index 3/UI P4 | 현재 수로와 동일한 Water 노드·ridePath에 속한다. |
| P5 회전 연결기 | index 2/UI P3에 기존 회전 동결 구조가 있음 | 실제 index 4/UI P5는 뿌리 성장 후 PULSE로 문을 여는 구간이다. |
| P6 최종 물레방아 | index 5/UI P6 | 수문, 채널 뿌리, 흔들 수로 준비가 엔딩 조건이다. 별도 마지막 직접 PULSE는 없다. |

따라서 후속 구현에서는 사용자 역할명과 실제 index를 함께 기록해야 한다. 번호만 보고 index 2를 수로로 바꾸거나 index 4의 뿌리를 회전기로 취급하면 기존 진행과 복구가 잘못 연결될 수 있다. 기존 6단계 재번호화는 별도 검증이 필요한 통합 변경이다.

## 3. 능력·타깃·진행 구조

### 능력과 타깃

`EFMapPlayer.cs:76–105`는 화면 중앙 카메라 ray로 능력 대상을 찾는다. `EFMapAbilityTarget` 링크가 있는 trigger는 조준에 사용할 수 있고, 관련 없는 trigger는 조준을 막지 않는다. 실제 고체 가림과 다른 대상은 차단한다. `EFMapPlayer.cs:114–132`는 입력 활성, 같은 world, 노드의 능력 조건, 플레이어 기준 거리, 플레이어에서 타깃까지의 가림을 확인한다.

`EFMapNode.cs:73–89`는 현재 stage와 완료 여부로 입력을 제한한다. BLOOM은 Flower/Vine/Root/Repair, PULSE는 Source 또는 성장 완료된 pulseAtRoot Root, FREEZE는 Debris/Slate/Bridge/Water에 적용된다. 마른 Water는 FREEZE를 거부하고 Bridge는 source 전원을 요구한다. FREEZE는 `EFMapNode.cs:107–115`의 토글이며 두 번째 입력으로 해제할 수 있다. 동시 동결 수 제한이나 전역 회수 시스템은 없다.

물리 지지 collider와 물 시각은 `EFMapNode.cs:147–153`에서 상태에 따라 바뀐다. Water의 Filled는 공급 노드의 Done에 의존한다. 기존 `EFMapAbilitySetup.Upgrade`는 Vine와 Water 노드가 각각 하나라는 `Single` 전제가 있으므로 새 Water 노드를 추가한 실험 씬에 무조건 재적용하면 안 된다.

### 정상 완료와 보조 인정

`EFMapWorld.cs:162–173`의 정상 완료는 해당 stage의 requirements, 도착 영역, 추가 사용기록을 확인한다. index 0은 꽃과 덩굴 사용, index 1은 파편 탑승 기록, index 3은 잎 슬라이드 사용 기록이 있다.

`EFMapWorld.cs:109–112,183–196`는 현재 stage 0..4의 도착 영역에 실제 도달하면 `TryPassage`로 보조 인정한다. 이 경로는 각도나 사용 이력을 다시 강요하지 않는다. 현재 stage만 한 번 완료할 수 있으며, `Completed`는 일반 진행 중 true에서 false로 회귀하지 않는다. 최종 index 5는 이 도착 보조 인정에서 제외된다.

`EFMapNode.cs:123–143`는 완료된 stage의 반복 회전·덩굴 움직임을 멈춘다. 다만 보조 인정된 노드를 모두 정답 상태로 새로 바꾸는 로직은 아니다. 완료 유지와 기계의 구체적 최종 자세는 후속 통합에서 각각 확인해야 한다.

### 추락 복구와 초기화

`EFMapWorld.cs:45`의 낙하 바닥은 index 3에서 -5, 그 외에는 `max(-10, Checkpoint.y - 10)`이다. `EFMapPlayer.cs:62`에서 바닥 아래로 내려가면 Respawn한다. `EFMapWorld.cs:203–217`의 Respawn은 탑승 시각·플레이어 위치를 복구하고 능력 준비 상태를 보존한다. R Retry는 미완료인 현재 stage의 노드와 체크포인트 저장 플래그, 해당 사용기록을 초기화한다. 이전 완료 stage는 초기화하지 않는다.

`EFMapCheckpoint.cs:11–15`는 현재 stage, 요구 노드 충족, 플레이어 trigger 접촉을 확인한다. **실제 접지 여부는 확인하지 않는다.** 새 높은 출발대 체크포인트는 공중 스침을 저장하지 않는 별도 검사가 필요하다.

`EFMapWorld.cs:218`의 전체 재시작은 현재 scene.path를 다시 로드한다. `EFMapWorld.cs:219`의 타이틀 복귀와 `EFTitleScreen.cs:10,30`의 시작 버튼은 기존 원본 타이틀/Map 경로다. 실험 씬에서 타이틀로 갔다 시작하면 원본 Map으로 진입한다. 원본 타이틀을 보존하려면 별도 실험 진입 경로나 안내가 필요하다.

## 4. 수로 확장의 기존 자원과 차이

사용자 P3 역할은 실제 index 3/UI P4다. `EFMapSetup.cs:88–108`의 기존 인과는 source4 PULSE→gate4 애니메이션 완료→Water.Filled→FREEZE→잎 E 탑승이다. `EFMapPlayer.cs:218–245`는 가속하는 잎을 직선 구간열로 이동시키고 capsule sweep으로 고체 충돌을 확인한다. 마지막 경로점 도달 후 SlideUsed를 기록하고 컨트롤러를 복구한다.

아래 좌표는 **Editor 구성 코드의 설정값**이며 이번 실행에서 측정한 착지 위치가 아니다. 모델 좌표에는 terrain 원점이 더해진다. 기존 감사 자료의 terrain 원점 `(9.450, 0.000, -3.142)`도 저장된 자료값이며 이번 플레이 실측으로 재확인하지 않았다.

| 항목 | 구성 코드의 terrain 상대 설정값 |
|---|---|
| stage 시작 | `(17, Ground(17,-42)+1.12, -42)` |
| 잎 경로 진입 | `(-24, 25.1, -42)` |
| 경사 끝 | `(-24, 12.85, -6.2)` |
| 공중 구간 | `(-24, 14.1, -0.5)` |
| 잎 도착 | `(-26, Ground(-26,8)+1.12, 8)` |

현재 경로는 기존 능선을 올라 높은 저수지 쪽에서 낮은 문 쪽으로 내려온다. 요청의 낮은 정비 마당에서 높은 출구와 막힌 틈을 관찰하는 관계와 같지 않다. 기존 배치를 단지 문구만 바꾸어 요청 P3 확장 완료로 보고하면 안 된다. 임시 도형과 분리된 공간을 이용한 실제 재배치, 조준 거리·가림·물리 경로 검증이 필요하다.

기존 수로에는 높은 잎 출발대 전용 체크포인트가 없다. 추락 시 펌프·얼음 상태는 유지되지만 복구 위치가 stage 시작일 수 있다. 준비된 수로를 반복시키지 않으려면 출발대의 실제 접지 체크포인트를 추가해야 한다.

## 5. 회전 연결기와 최종 퍼즐의 후속 위험

### 회전 연결기

기존 회전 Bridge는 index 2/UI P3다. `EFMapSetup.cs:84–87`의 설정은 initialAngle 55도, speed 27도/초이고 `EFMapNode` 기본 tolerance는 8도다. 이 수치는 실제 성공률이나 플레이어 반응 시간 측정값이 아니다. FREEZE 해제와 재가동은 이미 지원한다. A와 B를 같은 노드의 Frozen 토글로만 연결하면 B 판단을 위해 해제할 때 A 발판도 사라질 수 있다. A를 고정하거나 별도 latch로 유지하는 방식이 필요하다. 좁은 추가 각도·프레임 조건이나 새 전역 회수 시스템은 필요하지 않다.

### 최종 준비와 엔딩

`EFMapSetup.cs:117–130`의 최종 requirements는 source6, gate6, repair, swing이다. Swing는 Slate이므로 현재 전원이 없어도 FREEZE할 수 있다. `EFMapWorld.cs:81–103`은 마지막 stage에서 이 준비 조건이 충족되면 물 표시, 물레방아, 복원 애니메이션, 엔딩 카메라를 순서대로 시작한다. **최종 제어부 직접 도달·횡단·마지막 PULSE는 확인하지 않는다.** 따라서 요청의 최종 직접 입력 조건은 신규 구현 대상이다.

기존 복원 애니메이션의 `EFMapAnimation.Begin`은 중복 시작을 막는다(`EFMapAnimation.cs:42`). ResetPose와 Tick은 존재하나 건너뛰기 UI와 최종 상태 수렴 API는 없다. 정상 관람과 조기/후기 건너뛰기가 동일한 물·문·식생·빛·바퀴 상태를 만드는지 별도 검증해야 한다.

P3 물리 진행을 검증하지 못하거나 진행 차단이 남으면 이 상태에서 P5/P6를 통합 완료로 확장하면 안 된다. 그 경우 독립 구현·검토와 문서를 남기고, 실제 실행 가능한 범위와 차단 원인을 명시한다.

## 6. 보존 대상과 통합 시 금지 사항

- 원본 `Assets/Scenes/Everflow_Map.unity`, 원본 타이틀 이미지·능력 HUD와 기본 이동·점프·카메라·키 매핑을 보존한다.
- 카메라는 `EFMapCamera.cs`의 마우스 자유 시점, C 재정렬, 장애물 회피와 탑승 시선 보조를 사용한다. `EFMapWorld.cs:116–131`의 cinematic은 플레이어·추적 카메라를 비활성화하므로 연출 예외 복구를 함께 확인해야 한다.
- 원본 `EFMapSetup.Apply`, `EFPresentationSetup.Apply`, `EFMapAbilitySetup.Apply`는 고정 원본 씬이나 공유 프리팹·자산을 저장할 수 있다. 실험 씬 생성에 무조건 재사용하지 않는다.
- 공유 프리팹과 FBX 원본 변경 없이 실험 씬의 노드·복제·추가 자산으로 격리한다. 동일 이름의 실험 씬이 있으면 먼저 조사한다.
- 기존 보조 인정, 완료 유지와 최종 도착 자동 완료 금지를 보존한다. 전체 초기화와 현재 퍼즐 Retry는 서로 다른 동작으로 유지한다.

## 7. 실행 환경과 검증 출발점

`ProjectSettings/ProjectVersion.txt`는 Unity `6000.3.21f1`을 지정한다. `EditorBuildSettings.asset:8–15`에는 Title, Map, 6Puzzles가 활성화되어 있고 실험 씬은 이 조사 시점에 없다.

기존 `EFMapPlayTests.cs`는 입력 주입·카메라 조준·CharacterController 이동을 이용한 회귀 도구를 제공한다. 특히 기존 수로 경로와 최종 준비 후 자동 엔딩을 기대하므로, 새 통합 조건 검증으로 그대로 간주하면 안 된다. 사람의 마우스 조작, 초심자 테스트, 완료시간 측정도 대신하지 않는다.

후속 보고는 정적 검사, 컴파일, Editor 플레이, 빌드 생성, 빌드 실행을 각각 구분해야 한다. 이 기준 문서가 보장하는 것은 조사된 구조와 설정뿐이다.
